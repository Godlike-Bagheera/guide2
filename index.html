Введение

Этот гайд рассчитан на новичка, который хочет создать полноценное веб-приложение на РЕД ОС — российском Linux-дистрибутиве на базе RPM — не используя sudo (права администратора).

Мы построим классическую связку:

  • Бэкенд: Django + Django REST Framework (DRF) — Python-фреймворки для создания REST API
  • Фронтенд: React — JavaScript-библиотека для пользовательских интерфейсов
  • Аутентификация: JWT (JSON Web Tokens) через djangorestframework-simplejwt
  • Тестирование API: JSONPlaceholder — бесплатный фейковый REST API

Важно: Все команды выполняются от имени обычного пользователя. Если команда требует sudo — мы ищем альтернативу. РЕД ОС — RPM-дистрибутив, но мы обойдём системный dnf, установив всё в домашнюю директорию.

Prerequisites — что нужно знать до старта

🎓Минимальные требования

  • Базовое владение терминалом — команды cd, ls, mkdir, cat
  • Понимание, что такое файл и папка — куда что сохраняется
  • Умение открыть текстовый редактор — nano, gedit или VS Code
  • Браузер с DevTools — Firefox или Chromium, доступный по F12
  • Установленный Python 3.9+ — обычно есть в РЕД ОС по умолчанию
  • ~5 ГБ свободного места — для venv, node_modules, БД

Не требуется: опыт в Django, React, JWT, DRF. Мы разберём всё с нуля.

Архитектура приложения

Прежде чем начать, посмотрим на общую картину. Наше приложение состоит из двух частей, которые общаются по HTTP:

┌──────────────────────────────────────────────────────────────────┐
│                         БРАУЗЕР (localhost)                      │
│                                                                  │
│  ┌────────────────────────┐         ┌────────────────────────┐   │
│  │  React SPA (Vite)      │  HTTP   │  Django REST API       │   │
│  │  http://localhost:5173 │◄───────►│  http://127.0.0.1:8000 │   │
│  │                        │  JSON   │                        │   │
│  │  • Login.jsx           │         │  • /api/token/         │   │
│  │  • Notes.jsx           │         │  • /api/token/refresh/ │   │
│  │  • AuthContext         │         │  • /api/notes/         │   │
│  │  • axios + JWT         │         │  • /api/notes/:id/     │   │
│  └───────────┬────────────┘         └───────────┬────────────┘   │
│              │                                  │                │
│              │ localStorage                     │ ORM            │
│              ▼                                  ▼                │
│     ┌────────────────┐                 ┌────────────────┐        │
│     │ access_token   │                 │  SQLite DB     │        │
│     │ refresh_token  │                 │  (db.sqlite3)  │        │
│     └────────────────┘                 └────────────────┘        │
└──────────────────────────────────────────────────────────────────┘

     ПОТОК АУТЕНТИФИКАЦИИ:
     1. Пользователь вводит логин/пароль в React
     2. POST /api/token/ → сервер выдаёт {access, refresh}
     3. React сохраняет оба токена в localStorage
     4. Каждый запрос: заголовок Authorization: Bearer <access>
     5. Через 60 минут access истекает → 401
     6. axios автоматически POST /api/token/refresh/ → новый access
     7. Всё работает без перелогина пользователя

Про хранение токенов. В этом гайде мы используем localStorage — так проще для новичка и работает из коробки. Но в проде так делать не стоит: любой XSS украдёт токен. Реальный продакшн-паттерн — гибрид:

  • access_token (5–15 мин) — в памяти JS (React state), не в localStorage
  • refresh_token (7 дней) — в httpOnly Secure SameSite=Strict cookie
  • csrf_token (double submit) — в обычной cookie, читается JS

Плюсы: XSS не доберётся до refresh-токена, access быстро протухает и при утечке почти бесполезен, CSRF защищён отдельным токеном.

Часть 1. Бэкенд на Django

1. Введение в бэкенд

Мы создадим REST API для управления заметками. Каждая заметка имеет:

2. Почему без sudo и как это работает

В РЕД ОС команда dnf install требует прав суперпользователя — при попытке запуска без sudo вы получите ошибку: «Эту команду нужно запускать с привилегиями суперпользователя». Поэтому мы не будем использовать системный менеджер пакетов вообще.

Наш подход:

КомпонентКак ставимГде живёт
Python и зависимостиvenv~/projects/fullstack-app/venv/
Node.js и npmnvm~/.nvm/
Django-проектdjango-admin~/projects/fullstack-app/backend/
React-проектvite~/projects/fullstack-app/frontend/

Бонус: изолированное окружение — вы не сломаете систему и не получите конфликтов версий с уже установленными пакетами.

Что такое JWT? JSON Web Token — стандарт передачи данных между сторонами в виде JSON-объекта. Сервер выдаёт клиенту access token (короткоживущий) и refresh token (долгоживущий). 5. Django Admin — готовая админка из коробки

Одна из главных «киллер-фич» Django: панель администратора создаётся автоматически из ваших моделей. Не нужно писать HTML, forms и CRUD-логику — Django сгенерирует интерфейс для добавления, редактирования и удаления записей. Идеально, чтобы быстро наполнять базу данными и смотреть, как работают модели.

5.1. Включён ли Admin?

В свежем проекте всё уже включено по умолчанию. Проверьте два файла:

# backend/settings.py
INSTALLED_APPS = [
    ...
    'django.contrib.admin',       # ← сама админка
    'django.contrib.auth',        # ← пользователи и права
    ...
]

MIDDLEWARE = [
    'django.contrib.sessions.middleware.SessionMiddleware',
    'django.contrib.auth.middleware.AuthenticationMiddleware',  # ← без него admin не пустит
    ...
]python

Как это работает: админка построена на тех же моделях, что и ваш сайт. Таблица в браузере — это буквально Model.objects.all(), а форма редактирования автоматически строится из полей модели (CharField → текстовое поле, DateTimeField → виджет с календарём и т.д.).

5.4. Зарегистрируйте модель

По умолчанию в админке видны только Группы и Пользователи. Чтобы появились ваши заметки, зарегистрируйте модель в api/admin.py:

# api/admin.py
from django.contrib import admin
from .models import Note


@admin.register(Note)
class NoteAdmin(admin.ModelAdmin):
    list_display = ('id', 'title', 'owner', 'created_at')  # колонки списка
    list_filter = ('created_at', 'owner')                  # фильтры сбоку
    search_fields = ('title', 'content')                   # строка поиска
    ordering = ('-created_at',)                            # сортировка по умолчанию
    readonly_fields = ('created_at',)                      # только для чтенияpython

Старый стиль регистрации — admin.site.register(Note) — тоже работает, но класс с настройками удобнее. После сохранения страницы обновите админку: в разделе «Api» появится «Заметки» со списком, поиском и кнопкой «Добавить».

Не выставляйте /admin/ в интернет без настройки! Смените путь path('admin/', ...) на нестандартный, включите DEBUG=False, держите сильный пароль и выдавайте staff-права только нужным группам. Админка — самый лакомый объект для брутфорса.

Итого: createsuperuser → заход на /admin/ → регистрация модели через @admin.register — и у вас полноценная CMS для проекта за 5 минут. На этом этапе можно руками добавить тестовые заметки и проверить API-эндпоинты на реальных данных.

7.1. Модель api/models.py

Модель — это Python-класс, который описывает таблицу в БД. Django сам создаёт SQL-таблицу на основе класса.

from django.db import models


class Note(models.Model):
    """Заметка пользователя."""
    title = models.CharField(
        max_length=200,
        verbose_name='Заголовок',
    )
    content = models.TextField(
        verbose_name='Содержание',
    )
    created_at = models.DateTimeField(
        auto_now_add=True,
        verbose_name='Создано',
    )
    owner = models.ForeignKey(
        'auth.User',
        on_delete=models.CASCADE,
        related_name='notes',
        verbose_name='Владелец',
    )

    class Meta:
        verbose_name = 'Заметка'
        verbose_name_plural = 'Заметки'
        ordering = ['-created_at']

    def __str__(self):
        return self.titlepython

ForeignKey создаёт связь «многие к одному» — у одного пользователя много заметок. on_delete=CASCADE означает: при удалении пользователя удалятся его заметки. related_name='notes' позволяет обращаться к заметкам как user.notes.all().

from .serializers import NoteSerializer

class NoteDetailView(generics.RetrieveUpdateDestroyAPIView):

10. Углубляемся: что такое DRF под капотом

Разберёмся, что именно делают generics.ListCreateAPIView и ModelSerializer — вы будете видеть их постоянно.

10.1. Что делает ListCreateAPIView

Он объединяет два класса: ListModelMixin (GET-список) и CreateModelMixin (POST). Когда приходит запрос:

  1. Срабатывает get_queryset() — возвращает объекты из БД
  2. serializer_class конвертирует их в JSON
  3. permission_classes проверяет права
  4. Для POST вызывается perform_create() — там мы задаём owner

10.2. Что делает ModelSerializer

Он автоматически:

  • Читает поля из модели (title, content, created_at...)
  • Создаёт валидаторы (CharField → max_length=200)
  • Реализует create() и update()
  • Валидирует данные по типам

Ручной сериализатор для той же модели выглядел бы так (для сравнения):

class NoteSerializer(serializers.Serializer):
    id = serializers.IntegerField(read_only=True)
    title = serializers.CharField(max_length=200)
    content = serializers.CharField()
    created_at = serializers.DateTimeField(read_only=True)
    owner = serializers.CharField(source='owner.username', read_only=True)

    def create(self, validated_data):
        return Note.objects.create(**validated_data)

    def update(self, instance, validated_data):
        instance.title = validated_data.get('title', instance.title)
        instance.content = validated_data.get('content', instance.content)
        instance.save()
        return instancepython

ModelSerializer делает то же самое за 5 строк вместо 15 — и это только для одной модели.

14.1. axios-клиент с интерцепторами src/api/client.js

import axios from 'axios';

const api = axios.create({
  baseURL: '/api',
});

// ────────────────────────────────────────────
// REQUEST-интерцептор: добавляем Bearer-токен
// ────────────────────────────────────────────
api.interceptors.request.use((config) => {
  const token = localStorage.getItem('access_token');
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});

// ────────────────────────────────────────────
// RESPONSE-интерцептор: обновляем access при 401
// ────────────────────────────────────────────
api.interceptors.response.use(
  (response) => response,
  async (error) => {
    const original = error.config;

    // Если 401 и мы ещё не пробовали обновить
    if (error.response?.status === 401 && !original._retry) {
      original._retry = true;
      const refresh = localStorage.getItem('refresh_token');

      if (refresh) {
        try {
          const { data } = await axios.post('/api/token/refresh/', { refresh });
          localStorage.setItem('access_token', data.access);
          original.headers.Authorization = `Bearer ${data.access}`;
          return api(original);   // ← повторяем исходный запрос
        } catch (e) {
          // refresh тоже протух — разлогиниваем
          localStorage.removeItem('access_token');
          localStorage.removeItem('refresh_token');
          window.location.href = '/login';
        }
      }
    }
    return Promise.reject(error);
  }
);

export default api;javascript

Как это работает: интерцепторы — это middleware для axios. Request-интерцептор выполняется до каждого запроса, response-интерцептор — после каждого ответа. Мы используем их, чтобы не дублировать логику работы с токенами в каждом компоненте.

14.2. Контекст аутентификации src/context/AuthContext.jsx

import { createContext, useContext, useState } from 'react';
import api from '../api/client';

const AuthContext = createContext(null);

export function AuthProvider({ children }) {
  const [token, setToken] = useState(
    localStorage.getItem('access_token')
  );

  const login = async (username, password) => {
    const { data } = await api.post('/token/', { username, password });
    localStorage.setItem('access_token', data.access);
    localStorage.setItem('refresh_token', data.refresh);
    setToken(data.access);
  };

  const logout = () => {
    localStorage.removeItem('access_token');
    localStorage.removeItem('refresh_token');
    setToken(null);
  };

  return (
    <AuthContext.Provider value={{ token, login, logout }}>
      {children}
    </AuthContext.Provider>
  );
}

export const useAuth = () => useContext(AuthContext);jsx

19. Расширенная модель: теги и категории

Плоский список заметок — это скучно. Добавим категории (Many-to-One) и теги (Many-to-Many), чтобы понять, как работать со связями в Django ORM.

19.1. Обновлённая модель api/models.py

from django.db import models
from django.utils.text import slugify


class Category(models.Model):
    """Категория заметок — одна на много заметок."""
    name = models.CharField(max_length=80, unique=True)
    slug = models.SlugField(max_length=80, unique=True, blank=True)

    class Meta:
        verbose_name = 'Категория'
        verbose_name_plural = 'Категории'
        ordering = ['name']

    def save(self, *args, **kwargs):
        if not self.slug:
            self.slug = slugify(self.name)
        super().save(*args, **kwargs)

    def __str__(self):
        return self.name


class Tag(models.Model):
    """Тег — многие-ко-многим с заметками."""
    name = models.CharField(max_length=40, unique=True)

    def __str__(self):
        return self.name


class Note(models.Model):
    title = models.CharField(max_length=200)
    content = models.TextField()
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)
    is_pinned = models.BooleanField(default=False)

    owner = models.ForeignKey(
        'auth.User',
        on_delete=models.CASCADE,
        related_name='notes',
    )
    category = models.ForeignKey(
        Category,
        on_delete=models.SET_NULL,
        null=True, blank=True,
        related_name='notes',
    )
    tags = models.ManyToManyField(
        Tag,
        blank=True,
        related_name='notes',
    )

    class Meta:
        ordering = ['-is_pinned', '-created_at']
        indexes = [
            models.Index(fields=['-created_at']),
            models.Index(fields=['owner', '-created_at']),
        ]

    def __str__(self):
        return self.titlepython

Что тут нового:
• ForeignKey с SET_NULL — при удалении категории заметки остаются, у них просто очищается поле.
• ManyToManyField — Django сам создаёт промежуточную таблицу api_note_tags.
• Index в Meta — ускоряет сортировку и фильтрацию на больших таблицах.
• auto_now=True — поле обновляется при каждом save().

    permission_classes = [permissions.IsAuthenticatedOrReadOnly]
    search_fields = ['title', 'content']
    ordering_fields = ['created_at', 'updated_at', 'title']
    ordering = ['-is_pinned', '-created_at']

    def get_queryset(self):
        qs = Note.objects.select_related('owner', 'category').prefetch_related('tags')
        if self.request.query_params.get('mine') == '1' and self.request.user.is_authenticated:

        cat = self.request.query_params.get('category')

        tag = self.request.query_params.get('tag')
        if tag:

        return qs

24. Аутентификация: сравнение подходов

JWT — не единственный способ. Вот три самых популярных:

ПодходПлюсыМинусыКогда использовать
Session cookies Простой, безопасный (httpOnly), CSRF-защита встроена Плохо для мобильных, нужен sticky session на балансировщике Классический веб-сайт
JWT (то, что у нас) Stateless, работает с мобильными, легко масштабируется localStorage уязвим для XSS, нельзя отозвать токен SPA + API, мобильные приложения
OAuth2 / OpenID Позволяет вход через Google/GitHub, стандарт Сложнее настраивается Если нужен «Вход через Google»

Про безопасность JWT в проде:
• Хранить access в httpOnly cookie, а не localStorage
• Короткий access (5–15 мин), refresh в БД с возможностью отзыва
• Использовать RefreshToken.blacklist() из simplejwt для logout
• HTTPS обязателен, иначе любой может перехватить токен

class LogoutView(APIView):

25. База данных «на Python»: модели и миграции

В Django базу данных не нужно создавать руками в SQL. Вы пишете обычный Python-код — классы-модели, — а Django сам превращает их в таблицы. Файл называется models.py (частая ошибка новичков — искать его по имени modules.py; правильно — models, от слова «модель»). Лежит он в папке приложения: api/models.py.

25.1. Как это работает: модель → миграция → таблица

1. Пишете Python-класс в api/models.py
        │  python manage.py makemigrations api
        ▼
2. Django создаёт файл-миграцию
   api/migrations/0001_initial.py   (тоже Python-код!)
        │  python manage.py migrate
        ▼
3. Django выполняет SQL и создаёт таблицу
   в базе данных (по умолчанию — файл db.sqlite3)

Шаг 1. Откройте api/models.py и опишите таблицу классом:

# api/models.py
from django.db import models


class Book(models.Model):
    title = models.CharField('Название', max_length=200)
    author = models.CharField('Автор', max_length=100)
    pages = models.PositiveIntegerField('Страниц', default=1)
    published_at = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        return self.titlepython

Каждое поле класса — это колонка таблицы, а сам класс наследуется от models.Model. Колонку id Django добавит автоматически.

Шаг 2–3. Превращаем код в реальную базу двумя командами:

python manage.py makemigrations api   # создать файлы-миграции
python manage.py migrate              # применить их к БДbash

Аналогия: makemigrations — это «переводчик», который сравнивает ваш models.py с текущей базой и записывает разницу в файл миграции. migrate — «исполнитель», который применяет эти изменения к БД. Изменили модель — снова сделали две команды, и таблица обновится сама.

Проверить результат можно не выходя из Python:

python manage.py shellbash
>>> from api.models import Book
>>> Book.objects.create(title='Чистый код', author='Роберт Мартин', pages=464)
<Book: Чистый код>
>>> Book.objects.filter(pages__gt=400).values_list('title', flat=True)
<QuerySet ['Чистый код']>python

Никакого SQL — весь запрос к базе написан на Python. Это и есть Django ORM.

28. CORS глубоко: как браузер решает, кому можно ходить на ваш API

Мы уже подключали django-cors-headers в разделе 4 и делали прокси в разделе 13 — здесь наконец разбираем, что именно происходит. CORS (Cross-Origin Resource Sharing) — механизм браузера, который запрещает странице с одного адреса («origin») делать запросы на другой, если сервер явно не разрешил.

28.1. Что такое origin

Origin = протокол + домен + порт. Даже при одном домене разные порты — разные origins:

URLOriginСовпадает с Django (http://127.0.0.1:8000)?
http://localhost:5173localhost:5173❌ другой порт → CORS-проверка
http://127.0.0.1:5173127.0.0.1:5173❌ другой порт → CORS-проверка
https://mysite.rumysite.ru:443❌ другой домен → CORS-проверка
http://127.0.0.1:8000/app/127.0.0.1:8000✅ same-origin, CORS не нужен

Важно: CORS блокирует браузер, а не сервер. curl и Postman всегда получают ответ — поэтому API «работает из curl, но падает в React». Классическая путаница новичков.

28.2. Preflight-запрос OPTIONS

Для «непростых» запросов (JSON-тело, заголовок Authorization, методы PUT/DELETE) браузер сначала шлёт служебный OPTIONS-запрос — «можно тебе такое?» — и только получив разрешение, отправляет основной:

React (localhost:5173)                    Django (127.0.0.1:8000)
        │                                          │
        │  1. OPTIONS /api/notes/                  │
        │     Origin: http://localhost:5173        │
        │     Access-Control-Request-Method: POST  │
        ├─────────────────────────────────────────►│
        │  2. Access-Control-Allow-Origin:         │
        │     http://localhost:5173                │
        │     Access-Control-Allow-Headers: ...    │◄── CorsMiddleware отвечает
        │◄─────────────────────────────────────────┤      сам, ДО views и JWT
        │  3. POST /api/notes/  (реальный запрос)  │
        │     Authorization: Bearer eyJ...         │
        ├─────────────────────────────────────────►│
        │  4. 201 Created + CORS-заголовок         │
        │◄─────────────────────────────────────────┤

Именно поэтому CorsMiddleware стоит первым в MIDDLEWARE — он должен перехватывать OPTIONS раньше, чем Django дойдёт до маршрутизации, проверок токенов и вернёт 403/405 без CORS-заголовков.

28.3. Полный набор настроек django-cors-headers

# backend/settings.py
CORS_ALLOWED_ORIGINS = [
    'http://localhost:5173',
    'http://127.0.0.1:5173',
    'https://mysite.ru',
]

# вместо списка выше — регулярки (например, поддомены)
CORS_ALLOWED_ORIGIN_REGEXES = [
    r'^https://[a-z-]+\.mysite\.ru$',
]

    'accept', 'accept-encoding', 'authorization',
    'content-type', 'dnt', 'origin', 'user-agent',
    'x-csrftoken', 'x-requested-with',
]

CORS_EXPOSE_HEADERS = ['content-range']  # какие заголовки видны JS-коду

Звёздочка — зло. CORS_ALLOW_ALL_ORIGINS = True удобно в разработке, но в проде открывает ваш API любому сайту: вредоносная страница сможет читать данные авторизованных пользователей (при CORS_ALLOW_CREDENTIALS = True звёздочка вообще не работает — браузер её отвергает). Также нельзя смешивать * с конкретными origins.

28.4. Как диагностировать

  1. Console браузера: «Access to XMLHttpRequest … has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header» — значит сервер не прислал заголовок для этого origin.
  2. Network-вкладка (F12): найдите красный OPTIONS-запрос → Headers → сверьте Origin: со списком CORS_ALLOWED_ORIGINS — часто разница в localhost vs 127.0.0.1 или в слэше/протоколе.
  3. Проверка с терминала: эмулируем браузер:
curl -i -X OPTIONS http://127.0.0.1:8000/api/notes/ \
  -H "Origin: http://localhost:5173" \
  -H "Access-Control-Request-Method: POST"bash

В ответе должны быть строки Access-Control-Allow-Origin: http://localhost:5173 и Access-Control-Allow-Methods. Нет — corsheaders не подключён, не первый в MIDDLEWARE или origin не в списке.

28.5. CORS vs прокси: когда что применять

Прокси Vite (раздел 13)CORS-заголовки
Работаеттолько в dev (npm run dev)везде
СутьVite перешлёт запрос сам — origin для браузера не меняетсясервер разрешает чужой origin напрямую
Нужен лиудобно, но дублирует CORSобязателен на проде, когда фронт и API на разных доменах
Когда без него можно—фронт и API на одном домене (nginx раздаёт оба пути) — same-origin

Практика: в разработке держим и то, и другое (прокси спасает от мелких различий origins), на проде выбираем архитектуру — либо один домен с путями / и /api/ (CORS не нужен вовсе), либо два домена и честный белый список origins.

Итого: CORS — это диалог браузера с сервером через HTTP-заголовки. Ваш чек-лист: middleware первым, точный список origins (без звёздочки), credentials только с конкретными доменами, диагностика через F12 и curl-OPTIONS.

30. Глоссарий

venv

Virtual Environment — изолированная папка с Python-зависимостями, не засоряет системный Python.

nvm

Node Version Manager — менеджер версий Node.js, устанавливается в ~/.nvm без sudo.

DRF

Django REST Framework — библиотека для создания REST API. Даёт сериализаторы, viewsets, permissions.

JWT

JSON Web Token — самодостаточный токен с подписью. Состоит из header, payload, signature.

CORS

Cross-Origin Resource Sharing — правила, разрешающие браузеру делать запросы между доменами.

SPA

Single Page Application — одностраничное приложение. React загружает HTML один раз, дальше меняет DOM.

Прокси

Промежуточный сервер. Vite проксирует /api на Django — обход CORS в разработке.

Middleware

Прослойка обработки запроса в Django. Срабатывает до view и после.

Serializer

DRF-класс, конвертирующий объекты Python ↔ JSON. Также валидирует входящие данные.

ViewSet / GenericView

Классы представлений DRF. Generic — на каждое действие свой класс. ViewSet — всё в одном.

CBV (Class-Based Views)

Представления Django в виде классов. Дают наследование, миксины и переиспользование. В коде гайда: ListCreateAPIView, RetrieveUpdateDestroyAPIView — всё это CBV из DRF. Противоположность — FBV (function-based views), обычные функции.

Интерцептор

Функция axios, срабатывающая до или после каждого запроса. Мы используем для JWT.

ORM

Object-Relational Mapping. Django ORM превращает Python-классы в SQL-таблицы.

Миграция

Файл с описанием изменений схемы БД. Создаётся makemigrations, применяется migrate.

Queryset

Ленивый запрос к БД в Django. Не выполняется, пока не обратитесь к данным.

Rootless Docker

Docker, работающий без root. Можно запускать контейнеры без sudo на РЕД ОС.

Хук (React Hook)

Функция вроде useState, useEffect — добавляет состояние и жизненный цикл в функциональные компоненты.

Bootstrap 5

CSS-фреймворк с готовыми компонентами. Их можно копировать с официального сайта и вставлять в шаблоны Django — сайт собирается как конструктор.

django_bootstrap5

Python-пакет, который подключает Bootstrap 5 к Django-шаблонам тегами {% bootstrap_css %} и {% bootstrap_javascript %}. Ставится командой pip install django-bootstrap5.

models.py

Файл приложения Django с классами-моделями на Python. Каждый класс — таблица в базе данных; из него по командам makemigrations и migrate создаётся реальная БД.

Django Admin

Готовая панель управления (/admin/), которую Django генерирует из моделей. Включается createsuperuser + регистрация модели в admin.py.

PostgreSQL

Мощная открытая СУБД для продакшена. В Django подключается пакетом psycopg и 5 строками в DATABASES — код моделей не меняется.

Gunicorn (WSGI)

Продуктивный WSGI-сервер для Python-приложений. Заменяет учебный runserver; запускают обычно за nginx: gunicorn backend.wsgi:application.

Reverse-proxy (nginx)

Сервер-посредник перед приложением: принимает HTTP/HTTPS, раздаёт статику и проксирует динамические запросы на gunicorn.

Preflight (OPTIONS)

Служебный запрос браузера перед «непростым» CORS-запросом: спрашивает сервер, разрешены ли метод и заголовки.

34. Экспорт гайда

Этот гайд можно сохранить в PDF или DOCX прямо из браузера — стили для печати уже встроены.

PDF

  1. Нажмите Ctrl+P (или ⌘+P на Mac)
  2. В настройках печати выберите «Сохранить в PDF»
  3. Обязательно включите «Печать фона» (Background graphics) — иначе цвета и градиенты не сохранятся
  4. Отключите колонтитулы, если не нужны URL и номер страницы
  5. Нажмите «Сохранить»

Word / DOCX

  1. Откройте HTML-файл в LibreOffice Writer (он обычно предустановлен в РЕД ОС)
  2. Или в Microsoft Word: Файл → Открыть → выбрать HTML
  3. Сохранить как → формат .docx

Markdown

Скопируйте текст гайда, откройте в редакторе и оформите в Markdown. Или используйте pandoc для конвертации HTML → Markdown.

Совет для PDF: перед печатью переключитесь на светлую тему (☀️ в шапке) — PDF будет легче читать на бумаге и в e-reader. Тёмные темы тратят много краски.
